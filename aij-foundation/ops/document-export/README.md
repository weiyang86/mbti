# Controlled document image (AF-199)

Default is disabled. `DocumentExportExecutor` accepts only administrator construction with `enabled: true`, a normalized absolute Docker CLI path and an immutable **local image ID** `sha256:<64 lowercase hex>`. No environment switch, HTTP route, job/cost ledger, database or attachment integration is added. Treat the Docker socket and CLI as trusted operations infrastructure; never expose these construction options to a customer.

The image uses the exact Node digest in W16/RENDERER_DEPENDENCY_PLAN.json. It copies only the AF-197 approved runtime bundle into `/aij`, including `document-renderer-cli.js`, compiled renderer, resolved dependencies, fixed font and licenses. It installs/downloads nothing. The AF-197 bundle owner must supply that root-level CLI location; AF-199 never reads an unfinished AF-197 candidate. Production CLI accepts only the fixed stdin document protocol, with the font path embedded by AF-197.

After the real I197 integration is CODE_VERIFIED, the coordinator can run:

```sh
node scripts/document-export/build-runtime-image.mjs --root-integration /usr/bin/docker
```

This operations-only tool creates a fresh private build context, calls `buildRuntimeBundle`, rejects symbolic links/special files and oversized trees, copies the fixed Dockerfile, builds with `--network=none --pull=false`, returns the local immutable image ID and removes its own temporary directory. The pinned base must already be available in the isolated daemon; provision it separately. Docker build is root/coordinator exclusive, never a Worker or application operation. No tag, push or release is performed. Do not use a repository directory as the bundle/build context. `rootIntegration` is an explicit operations API safeguard, not an OS UID check.

Runtime: no inherited host environment, no mount/port/pull/network, read-only root, UID/GID 65534, all capabilities dropped, no-new-privileges, private IPC/cgroup namespace, pids 64, CPU 1, memory and swap total 512 MiB, bounded 64 MiB work and 16 MiB tmp tmpfs, no Docker logs. One admission across all instances in an API process; concurrent requests fail BUSY without a queue. Execution deadline is at most 15 seconds; cleanup then has separate bounded control calls (5 seconds each and 500 ms CLI reap grace), so the caller must await the returned cleanup result rather than treating deadline expiry as proof of container exit.

Only a matching random nonce/name/configured image/image ID/full container ID authorizes start/kill/removal. After removal, exact name and ID inspection must both prove absence. Unknown daemon state is CLEANUP_UNCONFIRMED; no artifact is returned and no broad container sweep occurs. An uncertain unreaped create is never reported clean. The process quarantines further admissions after unconfirmed cleanup; operations must resolve liveness and restart it before retrying; do not treat CLI termination as container termination.

Output is private RAM: a strict UTF-8 single JSON line, exact keys, canonical base64, matching format/MIME/version/size/hash/page metadata, basic file signature, at most 5 MiB decoded and 8 MiB stdout. Stderr/control output is separately bounded to 16 KiB. Structural rendering/page/font truth remains the trusted AF-197 renderer owner; envelope checks alone do not prove a valid ZIP/PDF. Errors contain only fixed outcomes, never stdout/stderr/body/path/stack. No implicit logging or persistence is added.

Worker validation: `node --test scripts/verification/document-export-executor.test.mjs` uses a private CLI collaborator, not Docker. Root live validation requires Linux, the real approved image and local Poppler/Python utilities:


The live gate parses actual production PDF/DOCX output, checks PDF text/fonts/pages and DOCX XML, then builds separate controlled test-only images for cgroup/UID/network/read-only assertions, actual OOM, deadline, cancellation, corrupt protocol and output cap. Probe images are distinct from production rendering evidence. It compares the exact pre/post nonce-labelled container ID set and removes only images it built; it never sweeps containers. Root must retain actual command/exit evidence and run formal `verify:task` plus applicable gates. Without opt-in this suite reports SKIP, not Linux acceptance. External suppliers remain DEFERRED_NOT_PASSED; full forty-goal/UI acceptance is NOT_RUN_TARGET_ACCEPTANCE.

Follow-up review hardening (candidate, live NOT_RUN): timeout and abort gates first inventory and inspect a fresh container using the unique probe image, exact full ID and name, random executor nonce, configured image ID and actual running/StartedAt state. Both ID and name inspections must agree while the adapter promise is still pending. Safe fixed running metadata is retained as TAP diagnostics before abort or waiting for the natural 15-second timeout; an early adapter return, failed observation or ambiguous container fails the gate. Observation-failure cancellation is cleanup only and cannot satisfy the case. No production observer/API or isolation flag was added or changed.

The cgroup v2 probe also requires `memory.swap.max` to equal `0`. Each probe build has unpredictable per-run and per-probe image labels; the final config therefore cannot reuse an existing image ID just because filesystem layers are cached. The gate records the full prebuild image inventory, verifies its new ID and both labels, and rechecks them immediately before deleting that exact ID without force. It records safe build/new-ID/removal metadata in TAP; an interrupted build with no confirmed ID remains a failed, unknown cleanup requiring root investigation. It never deletes existing or ambiguous images. Container inventory, each owned image and private scratch cleanup are attempted independently, with primary and cleanup failures combined rather than masked. The production bundle/image tool removes only its own context, never cached images, and likewise preserves build and context-cleanup failures together.

Operations path follow-up: the module's repository root is lexically normalized; the actual root and temporary parent are resolved through realpath before a fresh context is minted and verified. The AF197 destination is always the nonexistent `runtime` child of that fresh canonical context, never an operator-supplied existing directory. Successful bundles are removed with `removeRuntimeBundle` from the same imported AF197 module instance; its cleanup and the tool-owned context cleanup run independently and retain primary/cleanup errors. The filesystem path unit regressions are not renderer or Docker build evidence.
