## 1. 本次吸收后的结论

1. **本地集成是当前优先项。** 已有功能分卡验证很多，但当前 `scripts/base-development/config.mjs` 的固定 Base 配置关闭 clientAuth、storage 和插件，只适合原管理端范围；`apps/api/src/app.module.ts` 又根据这些能力决定装配客户端、文件、文档与AI。直接运行现有 Base 命令不能等于完整 AI 工作台已开放。应建立独立的 AI 集成配置，保持旧 Base 契约和数据不变。
2. **已有文档保存、不可变历史和导出可复用，先补真实缺口。** `apps/api/src/documents/personal-documents.service.ts` 已有当前权限、归属、expectedRevision、历史和审计；`client-document-manager.tsx:142` 仍明确局部再生成与历史恢复后续提供。历史恢复可优先组合原 GET version / PUT update，不能为它复制一套版本表或恢复账本。
3. **工作台与独立 SDK 的同一任务验收必须闭合。** AF191 原候选 Writer 已 STOP（`msg_183889068f99`），真实组合适配 I215 已完成，但14项原生目标尚未验。AF191记录累计1.5h、原预算3h，剩余1.5h；本次建议将累计上限明确调整到4h，最多新增2.5h。未获该调整前不能把旧卡当新卡重计。
4. **易修要求可靠服务端任务与人工决策，而非把行业工单搬入底座。** 现有 AsyncRuntime、通知投递意图、Workspace事务复检可复用；图定义允许 human-approval 不代表运行时已执行审批。目前 `ai-personal-workflow-linear-contract.ts:8–22` 仍只执行 start→agent→end。
5. **先修共用能力，再接行业。** 论文采购 / 零售 / 写手报酬、维修工单 / 库存 / 报价 / 开票分别归业务 owner；模型实际成本、支付事实、通知投递、任务与文件保留原唯一owner。

## 5. 如何更快，且避免返工

- 先冻结跨owner接口和明确拒绝路径，再并行写独立文件；每张卡只有一个Writer。不是对同一文档Service同时派三个人。
- 先复用已验证API、SDK、版本、任务和费用owner；有真实代码就不重做，占位字段 / 契约不当实现成果。
- 默认模型继续沿用当前配置，不按“前端 / 后端”标签盲切模型。任务边界、源码复用、依赖和验证调度是本批主要提速点。
- 独立纯测试并行；数据库、重型构建、Linux运行和原生浏览器各1；总控以自身租约验证候选。每卡正式门禁必做，同源同门禁通过后无新改动 / 失败 / 疑点不额外重复大构建。
- 候选积压最多2张，及时串行集成，避免全批最后才发现共享契约或父页面清理错误。共享依赖只引用真实I-*完成Task，不引用候选完成。
- 每卡预算含集成与修复；原失败和已耗时保留；超限拆卡。CODE_VERIFIED / 负责人接收 / 远端推送 / 发布分别记录。
